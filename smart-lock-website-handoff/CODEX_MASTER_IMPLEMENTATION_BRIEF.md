## 1. 项目定位与目标客户

### 1.1 品牌与定位

- 品牌名称：LOCKKING（项目暂定品牌名，正式商标使用权及品牌资料由用户确认）。
- 网站定位：Premium Smart Lock Manufacturer / Global B2B OEM/ODM Manufacturer。
- 核心宣传语：SMART LOCKS. BUILT FOR YOUR BRAND.
- 核心业务：智能门锁 OEM、ODM、品牌定制、产品开发、工程对接、批量采购合作。
- 主要市场：北美、欧洲及其他海外市场。
- 目标客户：海外品牌商、进口商、批发商、门锁渠道商、安防集成商、物业及多户住宅项目采购方。

### 1.2 网站的首要商业目标

让访问者快速理解：
- LOCKKING 提供什么类型的智能门锁及合作服务；
- 是否能够支持 OEM/ODM、定制和工程沟通；
- 如何了解产品、申请样品、提交项目需求；
- 如何联系商务团队并发起 NDA 沟通。

核心转化按钮应围绕：
- Request a Quote
- Discuss Your Project
- Request Samples
- Contact Our Team
- Submit OEM/ODM Inquiry

不要设置消费者购物车、在线零售结账、虚构价格或虚构库存。

### 1.3 品牌语气

专业、可信、克制、工程导向、国际化。避免夸张营销词、廉价促销风、过度科技炫光、阿里巴巴式密集信息堆砌。所有宣传都必须有事实依据。

## 2. 设计系统（必须统一执行）

### 2.1 颜色
- 主色 / 深海军蓝：#0B192C
- 深色背景：#07101A
- 辅助科技蓝：#2563EB
- 科技蓝 Hover：#1D4ED8
- 深灰正文：#1E293B
- 浅色背景：#F8FAFC
- 边框及中性色：采用清晰、低对比度的灰阶。

### 2.2 字体与排版
- 主字体：Inter。
- 备用字体：system-ui、-apple-system、BlinkMacSystemFont、Segoe UI、Roboto、Helvetica、Arial、sans-serif。
- 正文基准：16px，行高约 1.6。
- 标题：粗体或半粗体，层级清楚，避免过度紧缩导致可读性下降。
- 最大内容宽度：约 1280px。
- 页面区块上下留白：桌面端通常 80–120px；移动端按内容密度合理缩小。
- 圆角：主要使用 4–6px；较大的内容容器可适度增加，但避免消费级 App 的过度圆润。
- 阴影：轻量、克制，例如 0 4px 6px -1px rgba(0,0,0,0.05)。

### 2.3 视觉方向
- 欧美工业科技感、高端制造业、专业 B2B。
- 深海军蓝与科技蓝作为核心识别色。
- 采用大留白、清晰网格、精确对齐、真实产品摄影或高质量概念渲染。
- 图片应服务于产品、制造流程、工程能力和客户合作，不使用无关科技图库。
- 不得使用虚构的工厂照片冒充 LOCKKING 自有工厂实景。
- 不得用 AI 生成图冒充真实认证证书、真实测试报告或真实客户案例。
- 若暂时没有真实素材，使用设计良好的中性占位组件，并在后台/代码中标记待替换；正式页面不得显示丑陋的方括号说明文字。

### 2.4 响应式设计
桌面、平板、手机共用一套页面和组件，不建设独立移动子站。

至少覆盖以下测试视口：
- 手机：360px、390px、430px；
- 平板：768px、1024px；
- 桌面：1280px、1440px、1920px。

要求：
- 不出现横向溢出；
- 移动端使用可操作的汉堡菜单；
- 菜单打开/关闭、点击导航后关闭、Esc 关闭、适当的 aria 属性；
- 按钮和输入控件具有足够触控区域，建议不小于 44×44px；
- 卡片、表格、图片、表单在窄屏下合理堆叠；
- 不允许仅通过隐藏桌面导航就宣称移动端完成。

建议结构：

5. 工程与质量流程摘要：可展示建议流程图：需求沟通 → 方案评估 → 样品确认 → 测试验证 → 量产准备 → 交付。这是建议的合作流程，不得写成已经具备的具体设备或认证。
6. Why Partner With Us：使用可验证事实；无证据的数字、年限、客户 logo、评价全部禁止。
7. FAQ：OEM 与 ODM 的区别；是否支持品牌定制；如何申请样品；如何提交技术需求；MOQ 如何确定（回答以具体产品和项目评估为准，不编造统一数值）。

## 5. 技术实现要求

### 5.1 技术选型原则
- 现有设计采用 HTML5、Tailwind CSS CDN 和 Vanilla JavaScript。可以保留轻量化方向，但最终实现必须可维护、可构建、可测试。
- 优先在现有项目结构基础上选择简单、稳定、适合目标部署平台的实现。
- 如果仓库已经有成熟框架或构建配置，优先复用，不要无理由重建。
- 如果没有现成框架，可选择 Vite + 原生 JavaScript/TypeScript + Tailwind，或其他低复杂度方案。
- 不要为了炫技引入复杂 CMS、数据库或大型依赖。
- 组件、样式、页面内容、产品数据和语言字典应合理分离。
- 不允许把所有页面写成一个巨大文件。
- 保持清晰的 README、启动命令、构建命令和部署说明。

### 5.2 建议目录结构
可根据仓库现状微调，但交付结构必须清晰：

smart-lock-website-handoff/
- CODEX_MASTER_IMPLEMENTATION_BRIEF.md
- README.md
- website/ 或明确的实际应用目录
  - 页面/路由
  - components/
  - styles/
  - scripts/ 或 src/
  - data/（产品信息、语言字典、站点配置）
  - assets/
    - images/

  - tests/（如适用）

不要把最终可运行网站散落到仓库多个无关目录。所有网站代码集中在一个明确目录中。

### 5.3 公共组件
至少建立或复用 SiteHeader、DesktopNavigation、MobileNavigation、LanguageSwitcher、SiteFooter、PrimaryButton / SecondaryButton、ProductCard、SectionHeading、Breadcrumb（内页适用）、InquiryForm、FAQAccordion（如采用手风琴）、StatusMessage / FormFeedback。

### 5.4 表单后端与配置
用户尚未指定最终表单服务商、域名、邮箱服务和部署平台。因此：
- 不要虚构 API 地址、邮箱、数据库或第三方账号。
- 前端应实现清晰的 lead submission service / adapter，方便后续接入真实后端。
- 通过环境变量或安全的服务端配置保存 endpoint、邮件服务密钥等。
- 绝不能将 SMTP 密码、API key、私钥放入浏览器代码或 GitHub。
- 如果当前仓库没有后端，先实现可配置的 API 接口契约和清晰的未配置状态。
- endpoint 未配置时，表单不得显示提交成功；应明确提示当前暂不可提交，并提供不泄露数据的替代联系说明（仅当用户提供了真实联系方式后才能显示）。
- 如实现 serverless/API endpoint，必须进行服务端输入验证、限流/垃圾拦截和安全日志处理。
- 不得在未配置邮件收件地址和服务凭据前声称通知已发送。
